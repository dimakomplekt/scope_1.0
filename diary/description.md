# Описание

Архитектура программного осциллографа: фундаментальные принципы
В основе архитектуры лежит разделение на временные зоны с разной частотой обновления. Выделяются четыре основные зоны: зона реального времени с частотой дискретизации сигнала (до сотен килогерц), зона рендеринга с частотой обновления экрана (обычно 60 Гц), зона аналитики с частотой порядка 10–20 Гц и зона пользовательского интерфейса с частотой около 1 Гц. Эти зоны работают независимо и обмениваются данными через кольцевые буферы с минимальной блокировкой.

Ключевой принцип: чем выше частота обновления зоны, тем меньше операций она должна выполнять. Зона реального времени делает только запись incoming-сэмпла в буфер и обновление детектора триггера. Она не должна выполнять аллокаций памяти, операций ввода-вывода, вызовов графического API или сложных математических вычислений. Зона рендеринга читает из буфера и строит изображение, но делает это относительно редко. Зона аналитики работает с копией данных, а не с живым буфером, чтобы не блокировать запись.

Кольцевой буфер и управление данными
Основной структурой хранения является кольцевой буфер фиксированного размера. Размер буфера рассчитывается как произведение максимального временного окна на частоту дискретизации, умноженное на два-три для запаса. Буфер хранит как значения сигнала, так и временные метки для каждого сэмпла, что позволяет корректно работать с неравномерной дискретизацией.

Операция записи в буфер должна быть максимально простой: запись значения и времени по текущему индексу, сдвиг индекса, увеличение счётчика при необходимости. Индекс головы буфера должен быть атомарным или защищён минимальной блокировкой — лучше всего использовать атомарные операции процессора. Чтение из буфера для рендеринга может происходить без блокировки, если читающий поток не изменяет данные, а просто просматривает их.

Проблема неравномерной дискретизации
Реальные данные могут приходить с неравными интервалами времени. Это нормально, и с этим нужно работать правильно. Простейший и правильный подход — интерполяция отрезками между реальными точками при отрисовке. Это честно показывает отсутствие данных между измерениями. Альтернативный подход — ресемплинг с усреднением, когда неравномерный поток приводится к равномерной сетке путём накопления и усреднения сэмплов за равные временные интервалы. Ресемплинг требует отдельного буфера и выполняется в зоне реального времени или в отдельном потоке.

Режимы отображения
Различают два основных режима отображения: временная развёртка и периодная развёртка. Временная развёртка показывает фиксированное окно времени, например, последние N секунд сигнала. Она может быть с уходом влево (роллинг), когда новые данные появляются справа, а старые уходят влево, или статической, когда окно времени фиксировано, а сигнал внутри него обновляется целиком каждый кадр. Роллинг удобен для низких частот, статическая развёртка — для периодических сигналов.

Периодная развёртка показывает один или несколько полных периодов сигнала, наложенных друг на друга. Для этого необходимо детектировать начало периода — обычно по пересечению сигналом нулевого уровня снизу вверх. Точки одного периода накапливаются в отдельном буфере, и при завершении периода этот буфер добавляется в массив сохранённых периодов. При отрисовке все сохранённые периоды или их заданное количество выводятся на экран наложенными, что позволяет видеть вариации сигнала от периода к периоду.

Детектор триггера и претриггер
Детектор триггера определяет момент начала периода. Простейший и надёжный способ — детект пересечения заданного уровня (чаще всего нуля) снизу вверх. Для устойчивости к шуму можно добавить гистерезис: переход должен произойти с уровня ниже порога минус гистерезис на уровень выше порога плюс гистерезис.

Претриггер позволяет увидеть события, произошедшие до момента срабатывания триггера. Для этого используется отдельный небольшой кольцевой буфер, куда постоянно пишутся сэмплы. При срабатывании триггера содержимое претриггерного буфера копируется в начало основного буфера периода, после чего продолжается запись уже после триггера. Без претриггера вы увидите только момент события и то, что было после, но не то, что привело к событию.

Рендер-кэш и производительность отрисовки
Непосредственный пересчёт экранных координат всех точек буфера на каждый кадр неэффективен, когда в буфере десятки тысяч точек, а частота кадров ограничена 60. Поэтому применяется рендер-кэш — предвычисленный массив экранных координат, который перестраивается только при изменении параметров отображения (масштаба времени или напряжения, режима, размера окна) или при поступлении существенного количества новых данных. В остальных кадрах рендер просто пробегает по кэшированному массиву и рисует линии.

Когда точек в буфере значительно больше, чем пикселей по горизонтали экрана, имеет смысл делать децимацию — на каждый горизонтальный пиксель отображать минимальное и максимальное значение сигнала на соответствующем интервале времени, рисуя вертикальную линию. Это не только ускоряет отрисовку, но и позволяет видеть перегрузку и выбросы, которые иначе потерялись бы при прореживании.

Мёртвое время и пропуск событий
Важнейший концептуальный момент: осциллограф не видит сигнал постоянно. Между моментом завершения одного захвата и началом следующего есть интервал, называемый мёртвым временем. В программной реализации мёртвое время может быть огромным по сравнению с аппаратными приборами. Если частота дискретизации 60 кГц, а частота кадров 60, то за каждый кадр приходит 1000 сэмплов. Эти сэмплы непрерывны, но между кадрами нет пропуска — данные просто накапливаются в буфере. Настоящее мёртвое время возникает, если обработка данных в рендер-потоке или аналитике занимает столько времени, что поток сбора данных вынужден ждать. Поэтому критически важно, чтобы зона реального времени никогда не блокировалась.

Управление памятью и потоками
В зоне реального времени запрещены динамические аллокации памяти. Все буферы должны быть выделены заранее и иметь фиксированный размер. Запрещены вызовы функций, которые могут блокироваться: мьютексы (кроме быстрых spinlock), ввод-вывод, графические вызовы. Идеальная реализация зоны реального времени — это просто запись в предвыделенный массив и атомарный инкремент индекса.

Для обмена данными между зонами лучше всего использовать кольцевой буфер с атомарным указателем записи и константным указателем чтения. Если требуется полная изоляция — двойная буферизация, когда зона реального времени пишет в один буфер, а зона рендеринга читает из другого, и буферы периодически меняются местами под защитой короткой блокировки.

Синхронизация с частотой кадров
Не нужно пытаться синхронизировать сбор данных с частотой кадров. Зона реального времени работает в своём темпе, зона рендеринга — в своём. Рендер просто берёт текущее состояние буфера на момент начала кадра и рисует его. Если за время между кадрами в буфер добавилось 1000 новых точек — они все попадут в следующий кадр. Ничего страшного, если частота кадров ниже частоты дискретизации — это нормально и неизбежно.

Для ограничения частоты рендеринга используется таймер: прошедшее время сравнивается с целевым интервалом кадра, и при необходимости поток засыпает на остаток времени. Важно не использовать жёсткие задержки, которые могут рассинхронизироваться с частотой обновления экрана.

Обработка отсутствия сигнала
В начальный момент времени и при отсутствии сигнала детектор триггера не срабатывает. Нужно реализовать три состояния: ожидание первого триггера, накопление первого периода, нормальная работа. В состоянии ожидания на экран выводится сообщение с анимацией ожидания. При длительном отсутствии триггера можно автоматически переключиться в режим роллинга, чтобы пользователь видел хоть какой-то сигнал. Также полезно иметь кнопку принудительного триггера для отладки.

Масштабирование и авто-масштаб
Масштаб времени определяет, сколько секунд сигнала помещается на экран. При изменении масштаба перестраивается рендер-кэш. Масштаб напряжения определяет, сколько вольт соответствует полной высоте экрана. При авто-масштабе система отслеживает минимальное и максимальное значение сигнала в буфере и подстраивает масштаб так, чтобы сигнал занимал примерно 70–80 процентов высоты экрана, с небольшим запасом.

Подводные камни и их обход
Главный подводный камень — попытка делать всё в одном цикле с проверками времени. Это приводит либо к 100-процентной загрузке CPU, либо к пропуску сэмплов. Правильное решение — выделение зон либо в отдельные потоки с разными приоритетами, либо использование асинхронного ввода-вывода для АЦП.

Второй частый подводный камень — мьютексы в зоне реального времени. Любая блокировка может привести к пропуску сэмплов. Используйте lock-free структуры или хотя бы spinlock с очень коротким временем удержания.

Третий подводный камень — неверный расчёт размера буфера. Слишком маленький буфер приведёт к потере данных при большой временной развёртке. Слишком большой — к избыточному потреблению памяти и долгому перестроению рендер-кэша. Буфер должен покрывать как минимум два полных экранных окна при самой медленной развёртке.

Четвёртый — игнорирование временных меток. Если писать в буфер только значения без времени, то при неравномерной дискретизации или изменении частоты сэмплирования отображение будет искажено. Всегда храните время каждого сэмпла или хотя бы дельту относительно предыдущего.

Пятый — обновление UI-элементов слишком часто. Кнопка не должна обновляться 60 000 раз в секунду. Вынесите всё, что меняется редко, в отдельную зону с частотой не выше 10–20 Гц.

Шестой — выполнение тяжёлой математики (FFT, поиск пиков) на каждом сэмпле. Аналитика должна работать с копией данных и не чаще 10–20 раз в секунду.

Седьмой — использование интерполяции более сложной, чем отрезки между точками. Sin(x)/x имеет смысл только при очень высокой частоте дискретизации и чисто синусоидальных сигналах. Для общего случая отрезки работают отлично и не вносят ложных артефактов.

Восьмой — попытка нарисовать все точки буфера на каждом кадре. При 50 000 точек в буфере это будет тормозить. Используйте рендер-кэш и децимацию.

Девятый — ожидание, что сигнал всегда идеально периодический. Реальные сигналы содержат шум, джиттер, дрейф частоты. Детектор триггера должен быть устойчив к шуму (гистерезис), а режим периодов должен иметь возможность показывать несколько периодов наложенными, чтобы видеть вариации.

Десятый — отсутствие обработки ситуации, когда триггер не приходит долгое время. Нужен таймаут и переключение в режим роллинга или показ сообщения о отсутствии сигнала.

Итоговая схема взаимодействия
Зона реального времени непрерывно пишет сэмплы в кольцевой буфер. Зона рендеринга раз в кадр захватывает текущее состояние буфера (или использует двойную буферизацию), перестраивает рендер-кэш при необходимости и рисует сигнал и сетку. Зона аналитики периодически делает копию нужного фрагмента буфера и выполняет тяжёлые вычисления, обновляя при этом текстовые поля UI. Зона UI обрабатывает ввод пользователя, меняет параметры отображения (масштаб, режим) и обновляет редкие элементы интерфейса вроде часов и счётчика FPS.

Все зоны обмениваются данными через структуры с минимальной блокировкой: кольцевые буферы с атомарными индексами, флаги необходимости обновления кэша, разделяемые переменные для параметров отображения. Это позволяет достичь высокой частоты сэмплирования и плавного отображения без пропусков данных.


# Супер-фишки


1. Режим «Бесконечного Послесвечения» (Infinite Persistence)
   
Это одна из самых эффектных функций. В обычном режиме каждый новый захват данных стирает предыдущий. При включении режима послесвечения (Persistence) старые сигналы не исчезают, а "затухают" постепенно . Самые крутые осциллографы используют цветовое кодирование: редко возникающие шумы или глитчи отображаются тусклым или холодным цветом (например, синим), а основной сигнал, который появляется часто — ярким и теплым (например, красным) .


2. Минимизация «Мертвого Времени» (Dead Time)
   
Это самый нетривиальный момент. Осциллограф не может захватывать сигнал 100% времени: ему нужно время на обработку данных и "перезарядку" перед новым захватом. Это время называют "мертвым" (Dead Time), и в этот момент прибор слеп к сигналу.

Проблема: Даже у очень дорогих устройств при быстрых развертках (наносекунды на деление) "мертвое время" может составлять >99%! То есть прибор видит сигнал лишь 1% времени . Редкий глитч, который происходит в тот самый 1%, вы не увидите.

Решение: Топовые модели (Keysight InfiniVision) выжимают до 1 миллиона осциллограмм в секунду. Это радикально снижает шанс пропустить редкое событие .


3. Режимы Высокого Разрешения (High Res) и Наложения (Averaging)
   
Чтобы увидеть сигнал сквозь шумы, используются математические режимы:

High Res (Высокое разрешение): Процессор применяет цифровой фильтр к одному захвату, сглаживая шум и повышая вертикальное разрешение (обычно с 8 бит до 12–16 бит) без потери частоты дискретизации .

Averaging (Усреднение): Накладывает несколько последовательных захватов друг на друга, вычисляя среднее значение. Случайный шум исчезает, остается чистый периодический сигнал .

Peak Detect (Детектор пиков): Используется для ловли очень коротких выбросов. Прибор запоминает не просто "среднее" за интервал, а максимальное и минимальное значение, гарантированно фиксируя глитчи .


4. Интерполяция Sin(x)/x
   
Когда точек на период не хватает, просто соединить их прямыми линиями (Linear) недостаточно — синус получится пилообразным. Математическая интерполяция Sin(x)/x достраивает между реальными отсчетами идеальную синусоидальную кривую . Это стандарт для ВЧ-сигналов, позволяющий увидеть чистую форму сигнала даже при редкой сетке отсчетов.


5. Сложная Синхронизация (Trigger)
   
Запуск по фронту — это лишь вершина айсберга. Продвинутые приборы умеют ловить редкие и сложные события:

By Pulse Width (По ширине импульса): Сработать, если импульс короче 50 нс (ловля глитчей).

By Runt (По "недоimpульсу"): Сработать, если сигнал пересек один порог, но не дошел до второго.

By Logic (Логический запуск): Сработать при выполнении условия "Канал 1 = 1, Канал 2 = 0" (отладка цифровых шин) .


6. Roll Mode (Режим бегущей строки)
   
Вы его упоминали. Для низких частот (менее 1 кГц) стандартный режим неудобен, так как луч мечется туда-сюда. Режим Roll работает как кардиограмма: новые данные справа, экран плавно едет влево .

7. Глубокая Память и Математика (FFT/Мат. функции)
   
Объем памяти измеряется не в килобайтах, а в мегабайтах и гигабайтах на канал. Это позволяет записывать секунды сигнала на максимальной частоте, а потом "зумить" в любую точку с высоким разрешением . Кроме того, они умеют делать FFT (спектр анализатор), интегрирование (для получения энергетики сигналов) и даже фильтрацию прямо в реальном времени .

Резюме для вашего проекта
Понимая эту "высшую лигу", становится ясно, куда вы можете развивать свою программу:

Используйте интерполяцию отрезками сейчас, но держите в уме Sin(x)/x для будущих версий.

Режимы Average или Peak Detect — следующая ступень после просто отрисовки данных.

Главный "секрет" скорости — двойная буферизация и минимизация malloc во время захвата (обсуждали ранее).

"Мертвое время" — это физический предел даже для железа; в софтовом осциллографе он будет огромен, это нужно учитывать, когда вы захотите ловить глитчи.


# Ключевые моменты

1. Математика: 60 FPS vs 60 кГц сигнала
   
60 FPS = 16.6 мс на кадр
60 кГц = один сэмпл каждые 0.0167 мс (в 1000 раз чаще!)

За один кадр (16.6 мс) приходит ~1000 сэмплов сигнала.

### Что делать с этими 1000 точками за кадр?

``` cpp

// Update (вызывается для КАЖДОГО сэмпла - 60,000 раз в секунду!)
void update_scope(float value, Uint32 time_ms) {
```

``` cpp
        s->samples[idx] = value;
        s->timestamps[idx] = now;
        s->write_idx = (idx + 1) % 50000;  // атомарно на ARM/x86
        if (s->count < 50000) s->count++;
        
        // 3. Помечаем кэш как грязный (не блокируя)
        s->cache_dirty = true;  // volatile позволяет

        if (sleep_us > 0) {
            precise_sleep_us(sleep_us);
        }
    }
    return 0;
}
```

НЕ делай return по тикам внутри модулей. Вместо этого:

Источники данных (АЦП, симулятор) работают в своём темпе и просто кладут данные в очередь/буфер

Центральный апдейт вызывается как можно чаще (в главном цикле)

Каждый модуль имеет свою целевую частоту, но проверку делает диспетчер, а не модуль

Тяжёлые модули (осциллограф, FFT) вообще не должны быть в update-цепочке — у них отдельный поток или они работают по событию (раз в кадр)

Золотое правило: Никогда не заставляй модуль думать о времени. Время — забота диспетчера. Модуль просто выполняет свою работу по запросу.

``` cpp
typedef enum {
    UPDATE_HZ_1,      // 1 раз в секунду (часы, дата)
    UPDATE_HZ_10,     // 10 раз в секунду (анимация кнопок, счётчики)
    UPDATE_HZ_60,     // 60 раз в секунду (UI, позиции мыши, рендер)
    UPDATE_HZ_1000,   // 1000 раз в секунду (фильтры, простые ПИДы)
    UPDATE_HZ_60000,  // 60000 раз в секунду (осциллограф, АЦП)
    UPDATE_ALWAYS     // каждый вызов (критические вещи)
} UpdatePriority;

typedef struct {
    void (*callback)(void*);
    void *data;
    UpdatePriority priority;
    Uint32 last_update_us;

Updatable modules[100];
int module_count = 0;

// Центральный диспетчер (вызывается ~60 000 раз в сек из потока АЦП)
void dispatch_updates(Uint32 now_us) {
    for (int i = 0; i < module_count; i++) {
        Updatable *m = &modules[i];
        
        // Определяем интервал по приоритету
        Uint32 interval_us = 0;
        switch(m->priority) {
            case UPDATE_HZ_1:      interval_us = 1000000; break;
            case UPDATE_HZ_10:     interval_us = 100000; break;
            case UPDATE_HZ_60:     interval_us = 16666; break;
            case UPDATE_HZ_1000:   interval_us = 1000; break;
            case UPDATE_HZ_60000:  interval_us = 16; break;   // ~60 кГц
            case UPDATE_ALWAYS:    interval_us = 0; break;
        }
        
        if (interval_us == 0 || (now_us - m->last_update_us) >= interval_us) {
            m->callback(m->data);
            m->last_update_us = now_us;
        }
    }
}
```
