# Code


## Naming

Для всего собственного производства я использую snake_case, почти для всего я стараюсь давать полный нейминг, отображаюзщий смысл составляющей части кода, не использую сокращений в зоне логики, которая может быть неоднократно просматриваема для сохранения читаемости (к примеру - почти всегда panel_x_size вместо p_x_sz), для меня гораздо важнее сохранить читаемость и понимание происходящего в программе, спустя время после написания кода (при этом, скорость падает не особо сильно из-за автоввода, интеллисенса, копайлота)

Все константы КАПСЛОКОМ.

Все макросы КАПСЛОКОМ

Все объекты и классы (+ конструктор и деструктор) с заглавной большой буквы. Однако, все методы и все атрибуты, кроме константных атрибутов - с маленькой буквы.

Всё остальное - lowercase (за исключением случаев, когда я делаю что-то увязанное на что-то, что пытаются обозначать большими буквами, допустим - какое-то имя переменной, вроде "current_SDL_texture", где всё мелкое, кроме "SDL", потому что "SDL" принято звать "SDL", но в названиях файлов я всё равно даю на всё lowercase) 

Все похожие вещи в коде важно называть **ОДНОТИПНО** в плане размещения последовательности слов, к примеру, если у класса GUI-элемента есть, допустим, атрибуты ширины тени и ширины background-а, то важно проименовать их, как **"shadow_width_size"** и **"background_width_size"**, а не как, допустим **"shadow_width_size"** и **"background_width"** или **"width_size_background"** - это ускоряет использование взаимозаменяемого кода, позволяет активно использовать многострочную каретку и быстро писать похожие друг на друга куски кода для разных штук (даже в случае, когда они итак максимально схлопнуты в какую-то 1 функцию - всё равно надо передавать параметры в функцию и проще всего копировать вызов функции для 1 дела и чистить автозаменой или многострочной кареткой кусочек названия переменной под нужную в данный момент)


## Comments

Все комменты для частей кода, которые когда-то могут быть вынесены в отдельные библиотеки или могут быть реюзабельны в других проектах я пишу ТОЛЬКО НА АНГЛИЙСКОМ языке.

Если нужны какие-то быстрые временные пометки где-то, то я пишу их на русском, а потом убираю (или не убираю, как пойдет).

Между функцией и комментом к ней в .h файле не должно быть пропуска строки, чтобы VS CODE подтягивал описание при наведении на функцию (то же самое для структур, енамов, констант и прочего...). Если нужен коммент рядом с реализацией функции в .cpp, то между функцией и комментом к ней обязательно должна быть пропущена 1 строка (для того, чтобы этот коммент не перибивал коммент в .h файле).

Любые функции и методы, которые имеют возврат void и не имеют параметров при необходимости комментируются обычным однострочным комментом "// Функция такая-то делает то-то использую для того-то", где-то до 5 строк, если больше, то идёт переключение на обычный многострочный коммент "/* Функция такая-то делает то-то использую для того-то */".

Любые функции у которых есть любой возврат или у которых есть входные параметры комментируются многострочным комментарием со звёздочками и зонами @brief, @param,  @return, вроде примера ниже. **После последней строки коммента с содержимым обязательно добавляется одна пустая строка для более ясного визуального отделения коммента от функции** (как в примерах).

``` cpp

// Пример 1

/**
 * @brief Sets the fader's slot size.
 *
 * Updates the fader's slot width and height for rendering and layout.
 *
 * @param new_width New width of the fader's slot in pixels (> 120 px)
 * @param new_height New height of the fader's slot in pixels
 * 
 */
void set_slot_size(unsigned int new_width, unsigned int new_height);


// Пример 2

/**
 * @brief Returns the fader's slot  height.
 *
 * @return Height of the fader's slot in pixels
 * 
 */
unsigned int get_slot_height_size() const;

```

Я иногда раздаю вынесенные табуляцией под один уровень комменты в каких-то зонах, где есть много подряд объявлений чего-то, что требует коротких пояснений (как тут), при этом, стараюсь, чтобы это всё дело влезало по размеру (или было немного больше) больших разделителей (почти всегда половина экрана при комфортных для меня размерах буковок)

``` cpp

// =========================================================================================== БОЛЬШОЙ РАЗДЕЛИТЕЛЬ

// Control flags

button_access_type click_access_type;        // Button click access type for click callback logic permission


bool click_permission;                       // Button click permission flag


bool button_hovered;                         // Button hover state
void button_hover_check();                   // Button hover check method (to be called in the main loop)


bool button_clicked;                         // Button click state
bool button_clicked_tmp;                     // Button click state temp for callback block until the next click

bool push_mode_on;                           // Current push display mode
int press_offset;                            // Current press offset for push animation

```


## Structure

Все файлы начинаются с 1 однострочного коммента вроде // имя_файла.h или // имя_файла.cpp


Весь код делится на какие-то блоки, с использованием

1) Разделителя ***"// =========================================================================================== ИМЯ ЗОНЫ"*** для глобальных зон - размер выверен под половину моих дисплев при разделении на два окна, он позволяет мне ориентироваться с адекватной длиной строк кода. Весь код должен стараться быть меньше, равным или чуть больше по длине строки, в сравнении с этим комментом, чтобы я мог спокойно работать с разделением editor-ов пополам на дисплее.


``` cpp

// =========================================================================================== ИМЯ ЗОНЫ

void this_function_must_be_smaller_in_length_than_the_comment_upside_it()
{
    // ...
}

```

2) Разделителя ***"// ===== ИМЯ ЗОНЫ ====="*** для каких-либо глобальных зон внутри функции или класса

3) Разделителя ***"// Имя зоны"*** для каких-то локальных зон


**Между очень близкими по смыслу штуками в коде нет пропуска строк**

**Между не очень близкими, но всё же близкими по смыслу штуками пропущена 1 строка**

**Между всем остальным - пропуск двух строк, к примеру, как сделано тут:**


``` cpp

// my_sdl_fader.cpp


// =========================================================================================== IMPORT

#include "my_sdl_fader.h"

// =========================================================================================== IMPORT


// =========================================================================================== CONSTRUCTOR AND DESTRUCTOR

My_SDL_fader::My_SDL_fader()
{
    // Basic settings setter

    // Data

    this->fader_value = 0.5f;

    // Control flags

    this->slot_hovered = false;
    this->slot_clicked = false;
    this->slot_clicked_tmp = false;
    this->current_slot_state = DEFAULT_ES;

    this->knob_hovered = false;
    this->knob_clicked = false;
    this->knob_clicked_tmp = false;
    this->current_knob_state = DEFAULT_ES;


    this->delta_x_from_click_to_knob = 0;


    this->push_mode_on = true;
    this->press_offset = 0;

    // Sizes

    this->set_slot_size(120, 20);

    this->set_knob_size(20, 40);

    this->slot_border_width_size = 2;
    this->slot_border_radius_size = 5;

    this->knob_border_width_size = 2;
    this->knob_border_radius_size = 5;

// ...
}

```

Весь код в .cpp **старается соответствовать по последовательности реализации функций или методов той последовательности, которая была дана при их объявлении** в .h. Оттуда же можно (даже нужно) хватать введенные разделители и прочее.



## STYLE

Я сугубо по субъективным предпочтением почти никогда не делаю 

``` cpp

// Так

void function() {
    // ...
}

// Вместо такого

void function()
{
    // ...
}

// МНЕ (не вам) не нравится, когда делают так

void function() {
    // ...
}

// Мне НЕ ЖАЛЬ ЛИШНЕЙ СТРОКИ!!! Я БЕССОВЕСТНЫЙ.

```

Но при этом часто делаю:

``` cpp

// Так

void rectangle_draw_by_color(
    
    int x_render_point,
    int y_render_point,

    unsigned int width,
    unsigned int height,

    SDL_Color color,

    SDL_Renderer* renderer

);

// Вместо

void rectangle_draw_by_color(int x_render_point,
    int y_render_point,
    unsigned int width,
    unsigned int height,
    SDL_Color color,
    SDL_Renderer* renderer);

// И т.д.

```

В целом, при большом количестве параметров или условий я люблю навставлять пропусков строк, как в примере выше или тут:

``` cpp

// Element rectangle boundaries struct for logic like hover and click checks
struct element_rect_boundaries
{

    int left_boundary;
    int right_boundary;
    int top_boundary;
    int bottom_boundary;

};

```

Также можно делать с чем угодно, если кажется, что читаемость увеличится.


Во всяких коротких штукак с for, if и проч. можно пытаться делать ванлайнеры, вроде

```cpp

// Overflow check for the fader value
if (new_fader_value < 0.0f) new_fader_value = 0.0f;

```

Если есть возможность сделать ванлайнер, но он выходит каким-то тяжеловесным, то лучше его разбить на 2 строки, вроде:

``` cpp

if (this->slot_border_radius_size >= half_w && this->slot_border_radius_size >= half_h)
    this->slot_current_form = CIRCLE_EF;      

```

Если есть возможность сделать ванлайнер, но кажется, что может быть в эту зону с какой-то даже минимальной вероятностью будет добавлено что-то ещё (типо error-хендлера или доп. функционала), то вместо ванлайнера делается дефолтное условие:

``` cpp

// Допустим, тут вероятно появление какой-то проверки или чего-то ещё, я заранее прописал скобки, чтобы не городить их потом 

if (this->push_mode_on && this->press_offset <= 5)
{
    this->press_offset += 1;
}

```

В длинных условиях (не настолько уж длинных, чтобы писать ради избавления от них функцию с bool возвратом, но всё же длинных) КРАЙНЕ ХОЧУ видеть переносы и заключения составных условий в скобки (даже если скобки бессмысленны в плане порядка операций, ДЛЯ ДУШИ ХОЧУ СКОБКИ, ДЛЯ ДУШИ, ЧТОБЫ ДЫШАЛОСЬ ЛЕГЧЕ И НА СЕРДЦЕ СПОКОЙНО БЫЛО):

``` cpp

// Slot can't be circle
if ((new_width < 120 || new_height < 20) || 
    (this->slot_border_width_size > new_width / 2) || 
    (this->slot_border_width_size > new_height / 2) || 
    (this->slot_border_radius_size != 0 && this->slot_border_width_size > (this->slot_border_radius_size - 1)))
{
    std::cerr << "Wrong size value pass! Slot size ain't changed" << std::endl;
    return;
}

```
