## ПРОБЛЕМА 1. Причины падений

Найдено **пять** мест с неопределённым поведением. Два из них — прямая причина
описанных падений и зависаний, остальные три опасны, но срабатывают реже.

---

### 1.1 Главная причина. Неограниченный поиск назад в `build_fixed_time_render()`

Файл `scope.c`, строки 5402–5435 и точно такая же копия в
`build_fixed_period_render()`, строки 6024–6057.

```c
int window_start_idx = newest_idx;

bool history_finished = false;
bool enough_history = false;

while (!history_finished && !enough_history)
{
    window_start_idx--;

    unsigned int curr_idx = (window_start_idx + BUFFER_SIZE) % BUFFER_SIZE;
    unsigned int next_idx = (window_start_idx + BUFFER_SIZE + 1) % BUFFER_SIZE;

    history_finished = (buffer->samples[next_idx].time < buffer->samples[curr_idx].time);
    ...
}
```

**Что происходит.**

`window_start_idx` — знаковый `int`, уменьшается без нижней границы. Выход из цикла
возможен только по двум условиям, и оба ломаются на пустом или частично
заполненном буфере:

* `history_finished` определяется по «время пошло назад». После `memset` буфера
  (а это делает `scope_signal_buffer_clear()` при каждом выключении осциллографа)
  ВСЕ времена равны нулю, и `0 < 0` — ложь. Признак конца кольца не срабатывает никогда.
* `enough_history` требует найти пересечение нуля. В зоне нулей его нет.

Цикл проходит всё кольцо (384 000 элементов) и продолжает уменьшать счётчик.
Как только `window_start_idx` становится меньше `-BUFFER_SIZE`, выражение
`(window_start_idx + BUFFER_SIZE) % BUFFER_SIZE` даёт **отрицательный** результат
— в C остаток от деления отрицательного числа отрицателен. Дальше идёт
`buffer->samples[-N]`, то есть чтение памяти ДО начала девятимегабайтного массива.

**Все три симптома из задачи объясняются здесь же:**

* иногда молча читается чужая память → программа живёт дальше, но ведёт себя странно;
* иногда индекс попадает в незамапленную страницу → мгновенное падение;
* иногда цикл просто не завершается → «зависло».

---

### 1.2 Вторая причина. Отрицательный `int` в `unsigned`

Там же, строка 5518 (и 6140):

```c
unsigned int render_start_idx = window_start_idx;   // window_start_idx мог быть < 0
...
double zero_time = buffer->samples[render_start_idx].time;
```

Отрицательный `int`, приведённый к `unsigned int`, превращается в число порядка
4 миллиардов. Следующая же строка обращается к памяти за гигабайты от массива.
Это уже гарантированное падение, а не «как повезёт».

---

### 1.3 Третья причина. VLA на стеке, размер которого зависит от измеренной частоты

`scope.c`, `measured_data_update()`, строки 3231–3234:

```c
unsigned int samples_for_check = samples_per_period * periods_for_check + 1000;

float values[samples_for_check];        // VLA НА СТЕКЕ
```

Размер массива вычисляется из `measured_frequency` — то есть из той самой величины,
которую детектор периода регулярно определял неверно (проблема 2).

| измеренная частота | размер VLA |
|---|---|
| 196 Гц (норма) | 1 488 float ≈ 6 КБ |
| 20 Гц | 3 400 float ≈ 13 КБ |
| 1 Гц | 49 000 float ≈ 191 КБ |
| 0.5 Гц | 97 000 float ≈ 379 КБ |
| 0.1 Гц | 481 000 float ≈ **1.8 МБ** |

Стек потока в Windows по умолчанию — **1 МБ**. VLA не проверяется ничем: компилятор
просто вычитает размер из указателя стека, и первая же запись уходит за
защитную страницу.

Особая подлость в том, что **падение происходит не там, где ошибка**. Ошибся
детектор периода — упал анализатор measured-характеристик. По стеку вызовов
в отладчике причину не видно.

---

### 1.4 Четвёртая причина. Разыменование результата `Textbox_init()`

`scope.c`, 21 место в `scope_gui_renew()`, например строка 3822:

```c
used_scope->scope_render_data.scope_signature_textbox =
    *Textbox_init(used_scope->scope_render_data.main_color_2, 30 / (...));
```

`Textbox_init()` возвращает `NULL`, если шрифт не открылся — например,
папка `content/fonts` не скопирована рядом с exe. Разыменование `NULL`
происходит **до первого кадра**, без единого сообщения. Внешне это выглядит
как «приложение просто не запускается».

Плюс к этому: указатель нигде не сохраняется и не освобождается — 21 потерянный
`malloc` и 21 незакрытый `TTF_Font`. А поскольку `scope_gui_renew()` вызывался
дважды (из `scope_gui_init()` и повторно из `scope_init()`), а флаг
`scope_gui_need_update` не сбрасывался никогда — на самом деле 42 утечки.

---

### 1.5 Пятая причина. Чтение неинициализированных переменных

Три места:

* `drop_zc_accumulation()`, строка 1966 — `zero_cross_fill_status curr_zc_status;`
  не инициализируется, и при обоих заполненных zero-cross ни одна ветка `if/else if`
  ей ничего не присваивает.
* `measured_data_update()`, строки 3254–3255 — `curr_buffer_position` /
  `prev_buffer_position` объявлены без значения и заполняются цепочкой `if/else if`.
  Логика цепочку покрывает, но компилятор этого не доказывает, а результат —
  индекс в девятимегабайтный массив.
* `build_fixed_time_render()`, строки 5288 и 5330 — `time_unit_multiplier` и
  `signal_unit_multiplier` объявлены без значения, а ветка `default:` в `switch`
  ничего не присваивает.

---

### 1.6 Шестая, отдельная. Точность времени

`scope.h`: `float prev_clean_signal_time;` и `float last_not_noise_time;`.

Симуляционное время растёт монотонно от нуля. Через 15 минут работы оно
превышает 1000 с, а шаг представления `float` в этой точке — примерно `6e-5` с
при шаге дискретизации `2.08e-5` с. Три соседних сэмпла склеиваются в одно и то же
время, разность обнуляется, и длительности полуволн начинают врать тем сильнее,
чем дольше работает программа. Это не падение, но это ползучая деградация,
которую очень тяжело поймать: «сначала работает, а потом перестаёт».

---

### Анализ: почему такой код появился

Стоит разделить причины — они разные.

**Первая и вторая ошибки — след «поиска на ходу».** Видно по структуре: цикл
написан как «иди назад, пока не найдёшь то, что нужно», с флагами вместо
условия. Такая формулировка естественна, когда пишешь и одновременно
придумываешь алгоритм: сначала «идём назад», потом «а стоп, надо ещё проверить
конец данных», потом «а ещё zero-cross». Про то, что цикл вообще может не
найти ничего, в этой цепочке мыслей просто нет момента, когда об этом
подумать. **Кольцевой буфер тем и коварен, что у него нет естественного
конца — конец надо задавать самому, и это надо решить ДО того, как писать цикл.**

**Третья ошибка — след «сделаю с запасом».** Комментарий над VLA прямо говорит:
«оставляем запас, чтобы гарантированно вместить все точки окна». Мысль
правильная, но запас взят от величины, которая сама может быть любой. Классическая
ловушка: защита построена поверх недоверенных данных.

**Четвёртая ошибка — след несостыковки двух стилей владения.** Библиотека
текстбоксов написана в стиле «конструктор возвращает указатель», а осциллограф
хранит текстбоксы по значению. Строка `= *Textbox_init(...)` — это ровно то
место, где два стиля стыкуются, и стыкуются неверно. Написано один раз,
скопировано двадцать один.

**Пятая ошибка — след копипасты и «компилятор промолчал».** Все три места
компилятор ловит `-Wall`. Их просто никто не спросил.

**Шестая ошибка — след «float дешевле».** В DSP-коде это верно для значений
и неверно для времени. Время монотонно растёт, и относительная точность
`float` съедается абсолютной величиной.

### Как не допускать подобного дальше

1. **Собирайте с `-Wall -Wextra`.** Три из шести проблем компилятор показывает
   сам. В `new_sources/run.ps1` флаги уже добавлены. Это буквально две строки
   в скрипте сборки против вечера в отладчике.

2. **У любого цикла по кольцевому буферу должен быть счётчик шагов.**
   Не «пока не найду», а «не более `count` шагов, и если не нашёл — вернуть
   признак неудачи». Правило простое: *если в условии выхода из цикла есть
   данные — добавь второе условие выхода по счётчику.*

3. **Никаких VLA.** Особенно с размером из измеренной величины. Либо массив
   фиксированного размера (и явное ограничение окна сверху), либо `malloc`
   с проверкой. VLA не сообщают об ошибке — они просто портят стек.

4. **Индексы буфера — только знаковый `int`, приведение к `unsigned`
   запрещено.** А нормализацию писать не как `(i + N) % N`, а через явную
   проверку `if (i < 0) i += N;` — тогда отрицательное значение видно сразу.

5. **Любая переменная объявляется сразу со значением.** Особенно enum и индексы.

6. **Время — всегда `double`.** Значения сигнала — `float`, это нормально.
   Время — никогда.

7. **Функция, возвращающая указатель, проверяется на `NULL` в точке вызова,
   а не «когда-нибудь».** Если владение неудобное — оберните его один раз
   в хелпер (как сделано в `scope_textbox_create()`), а не повторяйте
   неудобство 21 раз.

8. **Отладочный `return` посреди функции — сразу помечайте как `// TODO REMOVE`.**
   В `detect_pattern()` такой `return` отключил половину алгоритма, а компилятор
   молчал, потому что предупреждение о недостижимом коде по умолчанию выключено.

## ПРОБЛЕМА 2. Модернизация пайплайна поиска периода

### Почему старый детектор ошибался

Три независимых поломки, каждая своя.

#### Поломка А. Сравнение уезжало в удвоенную копию буфера

Это главное. В `detect_pattern()`:

```c
int pattern_size = buffer->count;              // 64

for (int L = 2; L < pattern_size; L++)
{
    for (int i = 0; i < pattern_size; i++)     // i до 63
    {
        if (pattern_elements[i] == pattern_elements[i + L])   // i + L до 126
            equal_elements++;
    }
}
```

Массив удвоен (`ABC → ABCABC`), поэтому при `i + L >= count` сравнение
фактически идёт с `pattern_elements[i + L - count]`, то есть **с самим собой
со сдвигом `L - count`**.

Возьмём чистую строку `121212...` длиной 64 и `L = 62`. Сравнение превращается
в «элемент против элемента двумя позициями назад» — а для периода 2 это
**всегда совпадение**. `score = 1.0`.

То есть метрика систематически поощряла большие `L`. На чистом сигнале
побеждал `L = 2` только потому, что тоже давал 1.0 и проверялся раньше
(условие `score > best_score` строгое). Стоило шуму сбить пару элементов —
и `L = 2` давал 0.86, а какой-нибудь `L = 7` давал 0.93. **Детектор возвращал
7 вместо 2. Ровно то, что описано в задаче.**

#### Поломка Б. Классификация полуволн зависела от порядка

```c
for (i ...)
{
    if (pattern_elements[i] != 0) continue;
    pattern_elements[i] = current_pattern_element_number;

    for (j = i + 2; ...; j += 2)
        if (halfwave_distance(...) < 0.3)
            pattern_elements[j] = pattern_elements[i];
}
```

Полуволна присваивалась **первому подошедшему** классу, а не ближайшему.
Одна испорченная шумом волна получала новый номер — и все похожие на неё
дальше по буферу тоже уходили в этот новый класс. Строка `121212121212`
превращалась в `12121261212125` не из-за одной ошибки, а из-за лавины.

#### Поломка В. Отладочный `return` посреди функции

```c
    // TEST
    return median_pattern_len;

    float repeat_coverage = ...        // недостижимо
    if (best_score > 0.9f) return best_pattern_len;
    if (repeat_coverage > 0.8f) return median_pattern_len;
    return best_pattern_len;
```

Вся логика выбора между кандидатами была мёртвым кодом.

#### Поломка Г (питающая). Признаки полуволн были некорректны

* **Площадь** копилась как `halfwave_area += curr_x` — сумма СЫРЫХ значений.
  Зависела от dc-offset (при смещении 1 В полуволна из 100 точек получала
  100 В «бесплатно») и от того, сколько сэмплов детектор успел принять
  (шум заставляет пропускать точки → две физически одинаковые полуволны
  получали разную площадь).
* **Скорость** считалась как `speed = (speed + |v|) / 2` — это EMA с alpha 0.5,
  то есть величина почти целиком определялась последним сэмплом и от полуволны
  к полуволне гуляла в разы даже на чистом сигнале.
* Из-за этого нормировка площади в `halfwave_distance()` была бессмысленна
  по размерности: безразмерная сумма делилась на величину в В·с.

---

### Что предложено и реализовано

Пайплайн собран из четырёх слоёв. Каждый решает свою поломку.

#### Слой 1. Честные признаки полуволны

```c
// Площадь - истинный интеграл отклонения от центра
wpdf_ctx->curr_halfwave.halfwave_area += (float)((curr_x - curr_dc_offset) * dt);

// Скорость - считается ОДИН раз при закрытии полуволны
curr_halfwave->halfwave_smoothed_speed =
    (float)(fabsf(curr_halfwave->peak_value - curr_halfwave->trough_value) /
            curr_halfwave->halfwave_full_time);
```

Площадь теперь в В·с, не зависит ни от смещения нуля, ни от числа принятых
точек. Скорость — робастная величина «размах на длительность». Нормировка
в `halfwave_distance()` стала корректной по размерности.

**Почему это работает:** метрика различия полуволн наконец измеряет форму,
а не артефакты сбора данных.

#### Слой 2. Классификация по ближайшему классу, а не по первому подошедшему

`classify_halfwaves()`:

```c
for (int c = 0; c < classes_count; c++)
{
    if (class_reference[c].halfwave_type != halfwaves[i].halfwave_type) continue;

    float current_distance = halfwave_distance(used_scope, &class_reference[c], &halfwaves[i]);

    if (current_distance < best_distance)
    {
        best_distance = current_distance;
        best_class = c;
    }
}
```

Плюс эталон принявшего класса мягко подтягивается к элементу
(`HALFWAVE_CLASS_BLEND = 0.2`), чтобы одиночный выброс не утаскивал за собой
весь класс.

**Почему это работает:** лавинного эффекта больше нет. Испорченная полуволна
портит одну позицию строки, а не всё, что идёт после неё.

#### Слой 3. Два независимых свидетеля вместо одного

```c
symbolic_scores[L] = symbolic_pattern_score(halfwave_labels, count, L);
temporal_scores[L] = temporal_pattern_score(linear_halfwaves, count, L);

combined_scores[L] = 0.6f * symbolic_scores[L] + 0.4f * temporal_scores[L];
```

* **Символьный свидетель** — автокорреляция строки классов. Сравниваются
  ТОЛЬКО пары `(i, i + L)`, обе лежащие внутри реальных данных. Удвоение буфера
  убрано полностью — проблема «начало периода в произвольной точке кольца»
  решается разворотом кольца по времени (`linearize_halfwaves()`), а не копированием.
* **Временнóй свидетель** — нормированная автокорреляция последовательности
  ДЛИТЕЛЬНОСТЕЙ полуволн. Он вообще не зависит от того, правильно ли отработала
  классификация: даже если раскраска сбилась, длительности всё равно повторяются
  с шагом истинного периода.

**Почему это работает:** два свидетеля ошибаются по-разному. Шум, ломающий
классификацию, не ломает длительности; сбой длительности (пропущенный
zero-cross) не ломает классификацию. Чтобы обмануть систему, шуму надо
подделать оба свидетельства одновременно.

#### Слой 4. Три гейта на приём результата

**Гейт чётности и минимальных повторов:**

```c
int max_pattern_length = count / PATTERN_MIN_REPEATS;    // count / 3

for (int L = 2; L <= max_pattern_length; L += 2)
```

У периодического сигнала за период происходит поровну переходов вверх и вниз,
значит полуволн в периоде **всегда чётное число** — половина кандидатов
(включая злополучную «7») выкидывается сразу.

Потолок `count / 3`, а не `count / 2`: при `count = 64` кандидат `L = 30`
успевает «повториться» всего дважды и оценивается по 34 парам. Такая короткая
выборка на шуме легко даёт случайно высокую оценку. **Это подтвердилось
на живом тесте:** первая версия с потолком `count / 2` при шуме 28 % залипала
на `L = 30` и выдавала 78.5 Гц вместо 196. С потолком `count / 3` — 196.000 Гц
все 12 секунд.

**Гейт схлопывания кратностей:**

```c
for (int L = 2; L < best_pattern_len; L += 2)
{
    if (combined_scores[L] >= best_score - PATTERN_DIVISOR_TOLERANCE)
    {
        best_pattern_len = L;
        best_score = combined_scores[L];
        break;
    }
}
```

Берётся САМАЯ КОРОТКАЯ длина, качество которой не хуже лучшего больше чем
на 0.06. Строка `121212...` даёт одинаково хорошую оценку для `L = 2, 4, 6, 8` —
без этого шага победителем становится случайный из них, и показания периода
прыгают кратно. «При равном качестве выигрывает самый короткий» —
это стандартная формулировка задачи поиска фундаментального периода строки.

**Гейт приёма:**

```c
float weakest_witness = fminf(symbolic_scores[best_pattern_len],
                              temporal_scores[best_pattern_len]);

if (best_score < PATTERN_MIN_SCORE ||          // 0.72
    weakest_witness < PATTERN_MIN_WITNESS ||   // 0.60
    coverage < PATTERN_MIN_COVERAGE)           // 0.60
{
    // Период НЕ обновляем
}
```

Проверка `weakest_witness` принципиальна: взвешенная сумма позволяет сильному
свидетелю вытянуть слабого, поэтому дополнительно требуем, чтобы согласились оба.

**Ключевое решение:** если гейт не пройден — период просто **не обновляется**,
и на дисплее остаётся прошлое достоверное значение. Показать старое верное
значение лучше, чем свежее случайное. Именно это поведение видно в логе теста:
при шуме 28 % `conf` колеблется в районе 0.26–0.51, гейт всё отвергает,
и `F` спокойно держит 196.000.

#### Слой 5. Робастная статистика периода

В `detect_period()` — **медиана** вместо среднего по всем целым периодам буфера:
среднее ловит любой сбойный период целиком (пропущенный zero-cross удваивает
одно измерение и тянет среднее на 1/N), медиана к этому нечувствительна.

В `detect_pattern_and_period()` — **MAD-фильтр** по кольцу измерений:

```
1) медиана всех измерений
2) медиана модулей отклонений от неё (MAD)
3) выбрасываем всё, что дальше 3 * MAD
4) усредняем то, что осталось
```

MAD, в отличие от дисперсии, сам по себе не портится выбросами, поэтому
шаг 3 остаётся осмысленным даже когда половина измерений плохая. Раньше здесь
был грубый выброс максимума «если он больше среднего втрое» — пара сбойных
измерений подряд уводила среднее так, что «втрое» уже не срабатывало.

Плюс **гистерезис показаний** (`PERIOD_HYSTERESIS_PART = 2 %`): пока новое
значение отличается от текущего меньше чем на 2 %, оставляем старое. Без этого
последняя цифра на дисплее мельтешит каждый кадр, хотя сигнал не менялся.

## ПРОБЛЕМА 3. Стабильный рендеринг сигнала

### Почему дёргалось

Пять причин, все независимые.

1. **Триггер без гистерезиса.** Точка привязки искалась как «сэмпл, у которого
   сосед справа ниже dc, а сам он выше». На шумном сигнале таких точек за период
   набираются десятки, и **каждый кадр выбиралась другая**.

2. **Триггер искался от левой границы окна, а не от свежей точки.** При малейшем
   изменении dc или длительности окна точка старта прыгала на целый период.

3. **Привязка к целому сэмплу.** При 800 пикселях на 16 мс один сэмпл — это
   почти целый пиксель. Фаза кадр к кадру гуляла на этот пиксель, и ошибка
   накапливалась по всей ширине экрана.

4. **Выборка «первый сэмпл позже целевого времени».** Значение пикселя бралось
   как полусумма двух соседних сэмплов около найденного индекса. Если на пиксель
   приходится сто сэмплов — берутся два случайных из ста. Классический алиасинг:
   картинка каждый кадр разная, хотя сигнал не менялся.

5. **Никакого temporal-фильтра.** Каждый кадр строился с нуля, и остаточное
   дрожание на доли пикселя после округления до целых координат попадало на экран
   как есть.

### Что предложено и реализовано

Развёртка приведена к схеме, по которой работают настоящие цифровые
осциллографы (Rigol DS1000Z, Siglent SDS1000X — принцип один и тот же):

```
TRIGGER  ->  WINDOW  ->  DECIMATION  ->  PERSISTENCE
```

#### TRIGGER — `find_trigger_time()`

Честный edge-триггер с **гистерезисом**: фронт засчитывается только если
сигнал ДО него реально был ниже `level - hysteresis`, а ПОСЛЕ реально поднялся
выше `level + hysteresis`.

```c
if (!(value <= level && next_value > level)) continue;

// Проверка гистерезиса назад и вперёд на четверть периода
if (!went_low || !went_high) continue;
```

Момент пересечения уточняется **линейной интерполяцией**:

```c
crossing_time = time_1 + (double)((level - value) / (next_value - value)) * (time_2 - time_1);
```

Триггер получает **дробное** время, а не время сэмпла. Это убирает джиттер
в пределах одного сэмпла — причину №3.

Поиск идёт **назад от самой свежей точки**, поэтому окно всегда прибито
к последнему фронту, а не к случайному — причина №2.

Если триггер не найден (апериодический сигнал, мало данных, волна не выходит
за зону гистерезиса) — работает **AUTO-режим**: показывается свежий кусок
без привязки. Настоящие осциллографы поступают так же, экран не гаснет.

#### WINDOW

Левая граница = момент триггера минус pre-trigger часть экрана (10 %).
**Всё дальнейшее работает со ВРЕМЕНЕМ, а не с индексами** — поэтому уехать
за границы массива стало невозможно в принципе. Это же лечит краши 1.1 и 1.2.

#### DECIMATION — `fill_render_points_by_time_window()`

Для каждого пикселя собираются ВСЕ сэмплы, попавшие в его временной интервал,
и запоминаются минимум с максимумом:

```c
while (!data_exhausted && buffer->samples[idx].time < pixel_end_time)
{
    if (value < value_min) value_min = value;
    if (value > value_max) value_max = value;
    ...
}
```

Рисуется вертикальный штрих от min до max — так лечится алиасинг (причина №4).
Если сэмплов в пикселе меньше одного, значение берётся линейной интерполяцией
между соседями, а не округлением вниз.

**Почему это работает:** пиксель перестаёт быть «случайной точкой из сотни»
и становится честной сводкой того, что происходило за его время. Одинаковый
сигнал даёт одинаковую картинку.

#### PERSISTENCE

```c
int filtered_y = previous_y + (int)(RENDER_PERSISTENCE_BETHA * (float)(y_center - previous_y));
```

Экранная координата пропускается через фильтр первого порядка относительно
предыдущего кадра. При `beta = 0.35` картинка догоняет реальное изменение
примерно за три кадра — за 0.1 с, что глазом воспринимается как мгновенно,
а остаточное дрожание на доли пикселя размазывается и не ловится (причина №5).

Флаг `persistence_valid` сбрасывается при смене режима и при очистке экрана,
чтобы новый кадр не подмешивал в себя координаты старого сигнала.

#### Про ограничение FPS

Отдельно отвечу на вопрос из задачи — **ограничивать FPS этой части рендера
не нужно и вредно**. Дёрганье бралось не от частоты, а от того, что каждый
кадр строился по другой точке привязки. Понижение частоты сделало бы скачки
реже, но крупнее. Правильное лечение — сделать так, чтобы соседние кадры
были ПОХОЖИ, а не редки. Именно это делают триггер с гистерезисом и persistence.

Вариант «несколько буферов и вывести средний» тоже не подходит: усреднять надо
не буферы данных (они сдвинуты по фазе и усреднятся в кашу), а уже готовые
экранные координаты — после выравнивания по триггеру. Что и сделано.

## ПРОБЛЕМА 4. Аудит пайплайна фильтра

**Вывод: текущий пайплайн работает не так, как задумывался. Заявленной
адаптивности в нём нет вообще.** Ниже доказательство и минимальная переделка,
не уходящая от исходной идеи.

### Что было сломано

#### 4.1 σ не измеряла шум

```c
if (peaks_data->running_amplitude == 0.0 || isnan(...) || isinf(...))
    diff = 1;
else
    diff = fmaxf(signal_amplitude * 0.1f, 0.1f);

float diff_squad = diff * diff;
sigma_squad += filter_data->running_betha * (diff_squad - sigma_squad);
```

`diff` **не берётся из сигнала вообще**. Это просто десятая часть амплитуды.
Следствия:

* `sigma_squad` сходится к константе `0.01 · A²`, то есть `σ ≈ 0.1 · A`.
  EMA-интегратор дисперсии крутится вхолостую;
* порог `running_treshold = diff + k·σ = 0.1A + 0.1k·A`. При `k = 0.5`
  это жёстко зашитые **15 % амплитуды**;
* адаптивности нет: на чистом сигнале порог такой же широкий, как на шумном.

Отсюда прямо следует наблюдаемая граница: как только шум переваливает
за ~15–25 % амплитуды, он начинает пробивать порог, и детектор рассыпается.
**Это точно совпадает с описанным в задаче «работает до Aш/Aс ≈ 0.25».**

#### 4.2 Даже если бы σ считалась правильно, она всё равно не про шум

Дисперсия полного сигнала относительно центра для синусоиды равна `A²/2`,
то есть `σ ≈ 0.7·A`. Чистая синусоида амплитудой 5 В дала бы σ = 3.5 В.
Порог `k·σ` при таком σ съел бы всю волну. **Нельзя строить порог обнаружения
событий на дисперсии сигнала — только на дисперсии шума.**

#### 4.3 `renew_filter()` был недостижимым кодом

```c
float sigma = sqrtf(filter_parameters->running_sigma_squad);

float dc_confidence = 1.0f - dc_error / (MAX_ALLOWED_DEVIATION_IN_SIGMAS * sigma);
...
if (confidence >= 0.85) return;      // <- почти всегда
```

Нормировка шла на `3σ`, где σ привязана к амплитуде. Для сигнала 5 В это
`3 · 3.5 = 10.5 В`. Любая реальная невязка (доли вольта) на фоне 10.5 В давала
доверие 0.95–1.0, итоговый `confidence` всегда получался выше 0.85, срабатывал
ранний `return` — **и вся адаптация фильтра ниже никогда не выполнялась**.

#### 4.4 Медиана бегала за сигналом, а не за центром

```c
float v_max = 1.0f * 2.0f * (float)M_PI * (float)MAX_CONTROLLED_FREQ;   // 20 кГц
float max_delta_per_sample = v_max / (float)SCOPE_SAMPLE_RATE;
running_data->running_median.step = max_delta_per_sample * 0.001f;
```

Это ≈ 0.0026 В/сэмпл, то есть **125 В/с**. За половину периода 196 Гц
(122 сэмпла) медиана уезжает на 0.32 В — 6 % размаха для сигнала 5 В.
А медиана составляет 90 % от `dc_offset`.

**Центр «дышал» вместе с волной, а вместе с ним ездили точки перехода через
ноль.** Это второй, самостоятельный источник проблемы 2: длительности полуволн
разъезжались даже на идеально чистом сигнале.

### Что сделано (в рамках исходной идеи)

#### Шаг 1. Отдельная модель шума по второй разности

```c
float high_frequency_part = curr_x - 2.0f * prev_value_1 + prev_value_2;

noise_sigma_squad += noise_betha * ((high_frequency_part * high_frequency_part) / 6.0f
                                    - noise_sigma_squad);
```

Вторая разность полностью обнуляет постоянную и линейную составляющие: для
гладкого сигнала на частоте много ниже `Fs` она близка к нулю. Для
некоррелированного шума её дисперсия равна `6·σ_шума²` — отсюда прямая оценка
мощности шума за `O(1)`, без единого дополнительного буфера.

Приём известен как *noise estimation via second difference* (в астрономии
встречается под именем DER_SNR). Он ровно в стиле остального пайплайна:
одно состояние, одна EMA, никакой сортировки.

`running_sigma_squad` при этом сохранён и считается честно — он нужен
`renew_filter()` и диагностике.

#### Шаг 2. Порог от шума, зажатый по амплитуде

```c
float treshold = filter_data->k_treshold * noise_sigma;

float min_treshold = MIN_TRESHOLD_PART_OF_AMPLITUDE * current_amplitude;   // 1 %
float max_treshold = MAX_TRESHOLD_PART_OF_AMPLITUDE * current_amplitude;   // 25 %

if (treshold < min_treshold) treshold = min_treshold;
if (treshold > max_treshold) treshold = max_treshold;
```

Нижняя граница не даёт порогу схлопнуться в ноль на идеально чистом сигнале,
где любая цифровая рябь порождала бы ложные переходы. Верхняя не даёт порогу
съесть волну, когда оценка шума на переходном процессе временно взлетает.

**Вот здесь и появляется заявленная адаптивность:** чисто → порог 1 % амплитуды,
детектор чувствительный; шумно → порог растёт до реальных `3σ` шума,
детектор осторожный.

#### Шаг 3. Мёртвые зоны детектора тоже переведены на шумовую σ

```c
float trend_eps = 0.25f * noise_sigma;                 // было 0.0005f * sigma(сигнала)
bool not_noise = (deviation > 0.5f * noise_sigma);     // было 0.5 * sigma(сигнала)
```

Второе особенно важно: при σ полного сигнала порог «не шум» получался равным
`0.35·A`, то есть в зону «шум» попадала вся окрестность нуля — **ровно там,
где живут zero-cross-ы**. Детектор полуволн получал данные только с вершин
волны и по ним пытался ловить переходы через центр.

#### Шаг 4. Медиана переведена на время слежения за дрейфом

```c
// Стартовое значение
running_data->running_median.step =
    EXPECTED_SIGNAL_RANGE / (DC_TRACKING_TIME * (float)SCOPE_SAMPLE_RATE);
```

А в `renew_filter()` шаг уточняется, когда амплитуда и период уже известны —
из требования «за половину периода медиана не уходит больше чем на 2 % амплитуды»:

```c
float target_step = (MAX_MEDIAN_DRIFT_PART * amplitude_scale) / (0.5f * samples_per_period);
```

Это не «коррекция по невязке», а пересчёт кинематики оценщика под текущий сигнал —
и он выполняется всегда, до раннего `return`.

#### Шаг 5. `renew_filter()` — нормировка на амплитуду и прямая коррекция центра

```c
float error_scale = MAX_ALLOWED_ERROR_PART * amplitude_scale;   // 10 % размаха

float dc_confidence = 1.0f - dc_error / error_scale;
```

Вопрос «насколько центр промахнулся в долях размаха сигнала» — ровно тот,
ответ на который нам нужен. Ранний `return` перестал быть недостижимой веткой.

И добавлена прямая лёгкая коррекция:

```c
running_parameters->running_median.median +=
    DC_CORRECTION_PART * (measured_median - running_median.median);

running_parameters->running_mean.mean +=
    DC_CORRECTION_PART * (measured_mean - running_mean.mean);
```

Раньше при расхождении менялись только веса blend-а между средним и медианой.
Но если **обе** оценки уехали в одну сторону (а именно так и происходит при
несимметричном сигнале — например, у мультиволны генератора истинный DC около
+1.4 В), никакая перетасовка весов центр не вернёт: сколько ни смешивай два
смещённых числа, результат останется смещённым.

За один вызов центр сдвигается на четверть ошибки, полная сходимость —
несколько десятков миллисекунд, на картинке как скачок не видна.
Базовая идея «раз в промежуток времени слегка подстраиваем фильтр
по measured-значениям» полностью сохранена.

## ДОП. ЗАДАЧА 1. `build_scroll_render()`

Реализован. Полное описание концепции лежит комментарием прямо в коде функции,
здесь — сжато.

**Что это.** Roll-режим, он же режим самописца. Триггера нет вообще: правый край
экрана — это всегда «сейчас», картинка непрерывно уезжает влево, как лента
самописца или график загрузки процессора в диспетчере задач.

**Зачем нужен, если есть два других режима.** Триггерная развёртка показывает
СТОЯЧУЮ картинку: каждый кадр заново выравнивается по фронту, волна как будто
застыла. Идеально для периодического сигнала и бесполезно для медленного
апериодического — если сигнал меняется раз в несколько секунд, триггеру
не за что зацепиться. Roll показывает ИСТОРИЮ: видно, как параметр менялся
последние N секунд, видно одиночные события, видно дрейф. Реальные осциллографы
включают этот режим автоматически на развёртках медленнее ~50 мс/дел.

**Как работает.**

```c
double newest_time = buffer->samples[newest_idx].time;

fill_render_points_by_time_window(
    used_scope, render_data,
    newest_time - whole_screen_time,
    pixel_time, pixel_signal, width_pixels
);
```

Левая граница окна = время самого свежего сэмпла минус длительность экрана.
Всё. Дальше отрабатывает то же общее ядро выборки, что и в триггерных режимах.

**Почему картинка при этом не дёргается.** Дёрганье в триггерных режимах берётся
именно из перевыбора точки привязки. Здесь точка привязки одна и монотонно
растёт вместе со временем, поэтому кадр от кадра смещается ровно на
`(время между кадрами / pixel_time)` пикселей — картинка едет с постоянной
скоростью.

**Когда режим бессмысленен.** Когда сдвиг за кадр больше нескольких пикселей —
картинка превращается в мельтешение. Эта граница уже проверялась в
`change_scope_render_mode()` через `MAX_SHIFT_PER_FRAME`; проверка сохранена
и теперь корректно проскакивает roll на быстрых развёртках вместо ухода
в невалидный режим.

## ДОП. ЗАДАЧА 2. Разбиение `scope.c`

`scope.c` (7 997 строк) разбит на два файла при одном публичном заголовке:

| Файл | Строк | Что внутри |
|---|---|---|
| `scope_logic.c` | ~3 700 | время, буфер, рантайм-анализ, детектор полуволн, паттерн/период, measured, фильтр, публичный API объекта |
| `scope_gui.c` | ~4 000 | геометрия корпуса и сетки, текстбоксы, три режима развёртки, отрисовка, коллбеки кнопок |
| `scope.h` | 1 560 | **публичный** заголовок — приложению по-прежнему нужен только он |
| `scope_internal.h` | 210 | **приватный** заголовок реализации: только то, чем два .c обмениваются между собой |

Приватный заголовок — обычная практика для больших C-модулей (так устроены
и SDL, и большинство библиотек в стиле Google C++ Style Guide, где для этого
есть отдельное понятие *internal header*). Публичный интерфейс остаётся
маленьким и читаемым, а внутренняя кухня не засоряет пространство имён
пользователя модуля.

### Про вынос повторяющегося кода

Здесь держался баланс, о котором просили. Вынесено ровно то, где дублирование
было массовым и осмысленным:

| Новая функция | Сколько строк дублировалось |
|---|---|
| `fill_render_points_by_time_window()` | ~120 строк, продублированных между `build_fixed_time_render()` и `build_fixed_period_render()` (плюс ещё раз внутри каждой из них, в ветке `history_finished`) |
| `build_triggered_render()` | ~40 строк общей обвязки двух триггерных режимов |
| `get_whole_screen_time()` | ~30 строк расчёта масштаба времени, дублировавшихся дважды |
| `get_pixel_signal_scale()` | ~25 строк расчёта масштаба сигнала, дублировавшихся дважды |
| `scope_textbox_create()` | одна строка, но повторённая 21 раз и содержавшая баг |
| `find_sample_index_by_time()` / `find_trigger_time()` | новая логика, изначально общая для всех режимов |
| `linearize_halfwaves()` | ~30 строк разворота кольца, дублировавшихся в `detect_pattern()` и `detect_period()` |

Что **НЕ** выносилось сознательно:

* `scope_gui_renew()` (1 100 строк расстановки координат) — оставлен как есть.
  Формально там 17 почти одинаковых блоков на линии сетки и 12 на кнопки,
  но это код-таблица: его читают глазами сверху вниз, чтобы понять, где что
  лежит. Свернуть в цикл — значит превратить читаемую таблицу в непрозрачную
  генерацию, где чтобы узнать координату конкретной линии, надо считать в уме.
* `scope_render()` (550 строк вызовов отрисовки) — по той же причине: это
  сценарий отрисовки, порядок в нём и есть смысл (сначала задник, потом дисплей,
  потом свечение, потом сетка, потом сигнал).
* Пары `decrease_*` / `increase_*` в коллбеках — по 3–5 строк каждая, сворачивать
  нечего.
* Четыре case-а стейт-машины полуволн — они зеркальны, но не идентичны, и попытка
  их обобщить через флаг направления сделала бы самую сложную логику проекта
  нечитаемой. Вместо этого они приведены к строгой симметрии, чтобы расхождение
  между ними было видно глазом (что и позволило найти инвертированные условия).

Порядок реализации функций в обоих .c соответствует порядку объявления
в `scope_internal.h`, разделители зон перенесены. Все содержательные комментарии
сохранены; неактуальные дополнены пометками, что именно изменилось и почему.
Новые куски прокомментированы в том же стиле — пайплайн выполнения плюс
пояснение сложных мест.

## Как внедрять

1. Скопировать `scope.h`, `scope_internal.h`, `scope_logic.c`, `scope_gui.c`
   в `lib/scope/`, удалить старый `scope.c`.
2. **Необязательно.** Скопировать `global_inputs.c` в `lib/SDL2/global_inputs/` —
   там одно защитное изменение, не связанное с остальными. Можно пропустить.
3. Заменить `run.ps1` в корне (в нём обновлён список исходников
   и добавлены `-Wall -Wextra`).
4. Собрать. Предупреждений быть не должно.
